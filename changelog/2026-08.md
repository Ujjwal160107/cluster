- **Type:** break-glass kubectl (`kubectl exec ... grafana-cli admin reset-admin-password`,

- **Trigger:** the dashboard-uid-fix sync never progressed past `OutOfSync`. Root cause: the
  `grafana-create-dev-user` PostSync hook Job was `CrashLoopBackOff` with `dev: create failed
  (HTTP 401)` — its Basic Auth (`ADMIN_USER`/`ADMIN_PASSWORD` from `grafana-admin-credentials`,

  changed the secret value), so the container's committed env vars no longer matched runtime
  auth state.

  reset-admin-password admin`, forcing the sqlite-stored password back in line with the secret
  (idempotent, no git change needed since the secret was already right). Deleted the crash-looped
  hook `Job` so ArgoCD could recreate it clean, then cleared a stale stuck `operationState`
  (`waiting for completion of hook batch/Job/grafana-create-dev-user` against a Job that no
  longer existed) via `operation: null` and a hard refresh.
- **Verified:** `wget --header="Authorization: Basic $(echo -n <user:pass> | base64)"

### ~18:20 IST — monitoring: fixed Prometheus WAL checkpoint cleanup failing with permission denied since May
- **Actor:** agent (omp session) — user: "fix the monitoring namespace" -> (nothing currently
  Degraded/OutOfSync; asked user for the actual symptom) -> "Grafana/dashboard not loading in
  browser".
- **Type:** git commit (`k8s/monitoring/prometheus-deployment.yaml`) + break-glass kubectl
  cleanup (`kubectl exec` chown of stale root-owned WAL data, `kubectl rollout restart
  deploy/prometheus`).
- **Investigation:** Grafana itself loaded fine externally (curl to `grafana.upayan.dev`
  returned 200 after the expected 302 to `/login`; no errors in Grafana's own logs), so the
  reported "not loading" symptom pointed at data, not the UI. `prometheus` logs showed a
  recurring `ERROR ... delete old checkpoints ... unlinkat /prometheus/wal/checkpoint.00000209/
  00000000: permission denied` firing every 2h since deployment. `loki` had no equivalent
  errors.
- **Root cause:** `prometheus-deployment.yaml`'s container `securityContext` runs as
  `65534:65534` (`nobody`), but the PV's on-disk WAL segments and 31 stale
  `*.tmp-for-deletion` directories (oldest from May, ~1.3G) were owned by `root:root` —
  leftover from before the container's `runAsUser`/`fsGroup` was set. `fsGroup` only applies to
  newly created files, so it never retroactively fixed the old ones; Prometheus has been unable
  to actually delete superseded checkpoints/WAL segments since then, meaning stale TSDB data has
  been silently accumulating instead of being compacted away, which can degrade or corrupt
  historical query results feeding Grafana dashboards.
- **Fix:** added a root `initContainer` (`fix-permissions`, `busybox:1.36`) to
  `prometheus-deployment.yaml` that runs `chown -R 65534:65534 /prometheus` against the mounted
  `prometheus-data` volume on every pod start, so the ownership mismatch can't recur (e.g. after
  another manual/host-level write). Committed and pushed to `main`. As an immediate one-time
  cleanup (the initContainer only fixes ownership going forward, not the already-committed
  history), broke glass with `kubectl exec` to `chown -R 65534:65534 /prometheus` on the live
  pod, then `kubectl rollout restart deploy/prometheus` to pick up the new initContainer.
- **Verified:** after restart, `kubectl exec ... ls -la /prometheus/wal/checkpoint.00000209`
  and the `*.tmp-for-deletion` dirs show `nobody:nobody` ownership; no further
  `permission denied` lines in `prometheus` logs across a full checkpoint-cleanup cycle.

**Key finding #1 — `wait=true` bypasses the entire queue/worker

Ruby/Resque layer wasn't letting it. Root cause: **Resque forks a fresh
child process (full Ruby/Rails re-init) for every single job by
default** — this is a real, generic Resque gem behavior (not
Judge0-specific, and not exposed as a `judge0.conf` option, which is why
grepping the config found nothing). Set `FORK_PER_JOB=false` as a plain
environment variable on the `workers` service (bypasses `judge0.conf`
entirely — Resque reads `ENV["FORK_PER_JOB"]` directly). Re-ran the same

`workers` CPU now genuinely saturates both cores (peaked 198.8%/200%
across the full monitoring log) instead of idling at ~70% waiting on
`fork()` overhead — confirms the box's real CPU-bound throughput ceiling
is now actually being reached.
